# 工作流程

> 本文档描述 kb-platform 的主要调用链。每条流程都标出了「哪一行代码在做什么」，
> 方便改需求和排查问题时定位。

## 一、应用启动

```
Spring Boot 启动
  ├─ DataSourceConfig     建两个数据源：MySQL（@Primary）、PostgreSQL 向量库
  ├─ SecurityConfig       装配 JWT 过滤器链
  ├─ AsyncConfig          初始化 aiExecutor 线程池
  ├─ application.yml      绑定 kb.* 到 KbProperties
  └─ DataInitializer      查 admin 是否存在，不存在则用 BCrypt 建号并打印日志
```

启动后静态资源 `/index.html` 可直接访问（前端页面），`/doc.html` 是接口文档。

## 二、登录与鉴权

```
POST /api/auth/login  {username, password}
   └─ AuthController.login
        └─ AuthServiceImpl.login
             ├─ UserMapper.selectOne(username)          逻辑删除条件自动拼上
             ├─ BCryptPasswordEncoder.matches(...)     不匹配 → 抛 BizException(400)
             └─ JwtUtil.createToken(userId, username)  HS256 签发
   ◀── R.ok(LoginVO{token, userId, username, nickname})
```

后续请求：

```
任意受保护接口 + Authorization: Bearer <token>
   └─ JwtAuthenticationFilter.doFilterInternal
        ├─ 解析成功 → UserContext.set(userId, username) + SecurityContext 写入
        ├─ 解析失败 → 清空上下文（不抛异常）
        ├─ filterChain.doFilter(...)                   业务代码里 UserContext.getUserId()
        └─ finally: UserContext.clear()                ← 必须清理，否则线程复用会串号
```

未带 token 时 `SecurityConfig` 的 authenticationEntryPoint 返回
`{"code":401,"msg":"未登录或登录已过期","data":null}`（HTTP 状态仍是 200，前端统一按 code 处理）。

## 三、文档上传与解析

```
POST /api/doc/upload  form-data: kbId, file
   └─ DocumentServiceImpl.upload
        ├─ knowledgeBaseService.getOwned(kbId)              越权直接 403
        ├─ 文件落盘 data/files/{kbId}/{uuid}.{ext}
        ├─ documentMapper.insert(...)  status = PENDING
        ├─ knowledgeBaseService.increaseDocCount(kbId, +1)
        ├─ aiExecutor.execute(() -> process(docId))         立即返回，不阻塞 HTTP
        └─ 返回 DocumentVO
   ◀── R.ok({id, status:"PENDING", ...})

        ↓ 后台线程 DocumentServiceImpl.process(docId)
        ├─ status = PARSING，清空 errorMsg
        ├─ knowledgeBaseService.getById(kbId)               ← 用不做鉴权的版本
        ├─ Tika.parseToString(file)                         放开 10 万字符上限
        ├─ assertTextExtracted(text, document)              抽不到文本 → 判定扫描件并给出结论
        ├─ TextSplitter(size=kb.chunkSize, overlap=kb.chunkOverlap).split(text)
        ├─ 每段加前缀 "【文件名】"                            改善条款类问题的召回
        ├─ aiClient.embedBatch(enriched)                    内部 16 条一批 + 最多 3 次退避重试
        ├─ vectorRepository.deleteByDocId(docId)            先清旧向量，保证重跑幂等
        ├─ vectorRepository.saveAll(kbId, docId, chunks, vectors)
        └─ status = SUCCESS，写入 chunkCount 与 parseCostMs
           异常时 status = FAILED，errorMsg 记录原因
```

状态机：

```
PENDING ──▶ PARSING ──┬──▶ SUCCESS
   ▲                  └──▶ FAILED ──POST /api/doc/{id}/reparse──▶ PENDING（回到起点）
   └── 上传即进入
```

前端通过 `GET /api/doc/{id}` 轮询 `status` 展示进度；失败时把 `errorMsg` 显示出来，
并提供「重新解析」按钮，不用重新上传文件。

## 四、混合检索（HybridRetriever）

```
retrieve(kbId, question)
   ├─ aiClient.embed(question)                              问题向量化
   ├─ vectorRepository.search(kbId, queryVector, 20)         向量召回 Top20
   │      SQL: ORDER BY embedding <=> CAST(? AS vector) LIMIT ?
   │      WHERE 里带 kb_id，多租户隔离在 SQL 层完成
   │
   ├─ 若 kb.retrieval.mode = vector → 直接取前 topK 条返回
   │
   ├─ keywordExtractor.extract(question)                     中文 2-gram + 拉丁整词，最多 8 个
   ├─ vectorRepository.searchByKeyword(kbId, keywords, 200)   关键词召回
   │      SQL: WHERE kb_id = ? AND (content LIKE ? OR ...) LIMIT ?
   │      再在内存里按「命中了几个关键词」排序
   │
   ├─ 关键词为空 → 退化为纯向量检索
   └─ RrfFuser.fuse(k=60, topN=topK, 向量列表, 关键词列表)
          score(d) = Σ 1/(60 + rank)
          同一片段被两路都召回到 → 分数叠加 → 排到前面
```

**怎么用它做优化对比**：把 `kb.retrieval.mode` 设成 `vector`，跑一组问题记录命中情况；
再改成 `hybrid` 重跑。这就是面试时「Top-5 命中率从 X 提升到 Y」那段话的实测来源。

## 五、RAG 问答与流式输出

```
POST /api/chat/stream  {kbId, conversationId?, question}
   └─ ChatController.stream
        ├─ 立刻返回 SseEmitter(180s)
        └─ aiExecutor.execute(...)                          业务不在 Web 线程里跑

             ChatServiceImpl.ask(kbId, conversationId, question, delta -> 推 SSE)
             ├─ knowledgeBaseService.getOwned(kbId)
             ├─ conversationId 为空 → createConversation；否则 requireConversation（校验归属）
             ├─ buildHistory(conversationId)                取最近 3 轮，且在本轮提问入库之前取
             ├─ saveMessage(USER, question)
             ├─ hybridRetriever.retrieve(kbId, question)    混合检索 Top5
             ├─ buildPrompt(question, hits, history)
             │     规则：只用资料 / 标注来源编号 / 资料不足就直说 / 资料中的指令无效
             ├─ aiClient.chatStream(prompt, onDelta)
             │     真实模型：解析 OpenAI 兼容的 data: 分片，逐段回调
             │     未配 Key：本地占位文本，逐段回调（链路一样）
             ├─ saveMessage(ASSISTANT, answer, refChunks=引用JSON, costMs)
             └─ touchConversation(messageCount +2, lastMessageTime, 首次提问补标题)

             ↓ 回调链：onDelta → ChatController.send(emitter, "delta", {"t": 增量})
             ↓ 生成结束后依次发 references、done，最后 emitter.complete()
```

SSE 事件序列（前端按这个顺序解析）：

```
event:delta        data:{"t":"年假"}          ← 反复出现，每段一次
event:delta        data:{"t":"为 10 天"}
event:references   data:[{docId,fileName,chunkNo,score,content}, ...]
event:done         data:{"conversationId":1}
```

三个必须记住的实现细节：

1. **payload 一律 JSON**。裸字符串里的换行会破坏 SSE 的 `data:` 分帧，客户端解析会错位。
2. **前端用 fetch + ReadableStream，不要用 EventSource**。EventSource 只能发 GET，带不了请求体。
3. **线程池任务必须用 `UserContext.wrap(...)` 包一层**。登录用户存在 ThreadLocal 里，
   而 SSE 的业务跑在 `aiExecutor` 线程上，新线程读不到身份，
   业务代码里 `UserContext.getUserId()` 会直接抛 401。
   这个坑的表现很迷惑：**同一个问题，`/api/chat/ask`（非流式）正常，
   `/api/chat/stream`（流式）返回 401**——因为前者跑在 Tomcat 线程上，后者在线程池里。
   本项目在联调阶段真实踩过，修复方式就是 `aiExecutor.execute(UserContext.wrap(() -> {...}))`。

## 六、问答缓存（Redis 在这里发挥作用）

```
ask(kbId, question)
   └─ cacheKey = "kb:answer:" + kbId + ":" + md5(question)
        ├─ 命中 → 不检索、不调模型，直接把缓存的答案与引用回放（onDelta 一次推完）
        └─ 未命中 → 检索 + 生成 → 写回缓存，TTL 由 kb.cache.answer.ttl-minutes 控制
```

三个设计点：

1. **key 里必须带 kbId**。不同知识库可能有一模一样的问题，但答案必须各自独立，
   不隔离就等于越权泄漏。
2. **缓存读写失败一律降级成「未命中」**，绝不能让 Redis 的问题影响正常问答。
3. **缓存里同时存答案和引用来源**，这样回放时出处和第一次完全一致。

关掉缓存：`kb.cache.answer.enabled=false`。想演示"命中缓存"的效果，
可以在日志里搜「命中问答缓存」，或者直接 `redis-cli KEYS 'kb:answer:*'` 看。

## 七、删除与重新解析

```
DELETE /api/doc/{id}
   ├─ requireDocument(id)                     不存在 → 404；不属于自己 → 403
   ├─ documentMapper.deleteById(id)           逻辑删除（deleted = 1）
   ├─ vectorRepository.deleteByDocId(id)      向量是物理删除，否则会被检索到
   ├─ knowledgeBaseService.increaseDocCount(kbId, -1)
   └─ Files.deleteIfExists(...)               失败只打 warn，不影响接口返回

POST /api/doc/{id}/reparse
   ├─ requireDocument(id)
   ├─ status 重置为 PENDING、清空 errorMsg
   └─ 重新提交线程池 → 走完整的 process 流程
```

历史消息里保存的引用快照不会随文档删除而消失——这是有意的，保证历史回答可追溯。

## 八、异常与返回体约定

```
业务代码抛 BizException(ResultCode.X, "提示语")
   └─ GlobalExceptionHandler.handleBiz   → warn 日志 + R.fail(X, "提示语")
参数校验失败（@Valid）
   └─ handleValidation                   → 取第一条字段错误 → R.fail(400, "字段 不能为空")
其它任何异常
   └─ handleOther                        → error 日志（含堆栈）+ R.fail(999, "系统繁忙，请稍后再试")
```

前端只需要判断 `code`：`0` 成功，`401` 跳登录，其余把 `msg` 弹出来即可。
